# Чек на удачу — промо-приложение

Тестовое задание: веб-приложение промо-акции. Покупатель регистрирует чек, модератор проверяет его через стандартную админку Django.

**Стек:** Python 3.12, Django 5.0, PostgreSQL 16, Docker Compose. Фронтенд — чистый HTML/CSS/JS без сборщиков.

## Быстрый старт

```bash
cp .env.example .env          # Windows: Copy-Item .env.example .env
docker compose up --build
```

Сайт: http://localhost:8080 (порт 8080, а не 8000 — на многих Windows-машинах 8000 зарезервирован Docker Desktop / Hyper-V).

**Создать модератора:**

```bash
docker compose exec web python manage.py createsuperuser
```

Админка: http://localhost:8080/admin/ — раздел «Промо-акция "Чек на удачу"».

**Остановка:** Ctrl+C. Полная остановка с сохранением БД: `docker compose down`. Удалить БД и медиа: `docker compose down -v`.

## Что реализовано

### Обязательная часть

- Модель `Receipt`: ФН, ФД, ФП, дата/время покупки, сумма, статус (pending/accepted/rejected), причина отказа, пользователь, дата регистрации, фото (необязательно).
- Форма регистрации чека с полной серверной валидацией:
  - дата покупки входит в период акции (границы из `.env`, включительно);
  - сумма ≥ `PROMO_MIN_AMOUNT` (по умолчанию 1000 ₽);
  - ФН+ФД+ФП уникальны (частичный UNIQUE в БД + валидация формы);
  - новый чек всегда в статусе `pending` (форсируется в `save()`).
- Личный кабинет: список своих чеков (дата, сумма, статус, причина отказа), сортировка по дате покупки (новые сверху), пагинация по 10.
- Стандартная админка Django для модератора (staff-флаг).
- `GET /api/receipts/` — чеки только текущего пользователя.
- Фронтенд: два экрана по макету Figma, адаптив до 375px (таблица на мобилке превращается в карточки, горизонтального скролла нет).
- JS-валидация полей до отправки + отправка через fetch, ответ сервера показывается на странице (успех и ошибка разными блоками).

### Сверх задания (отмечено специально)

- **Поле «вставить строку из QR-кода»** — парсит `t/s/fn/i/fp`, заполняет поля автоматически. Парсер есть и на сервере (`promo/services.py`), и на клиенте (`static/js/form.js`).
- **Загрузка фото чека** с проверкой MIME-типа (JPG/PNG/WEBP) и размера (`PROMO_MAX_PHOTO_MB`, по умолчанию 5 МБ).
- **CSV-выгрузка принятых чеков** из админки (action на выбранных строках, с BOM для корректного открытия в Excel).
- **Тесты** (21 шт.): валидация формы, изоляция пользователей в кабинете и API, защита от утечки чужих чеков через query-параметры.
- **Частичный UNIQUE-constraint** в БД: разрешает повторную подачу отклонённого чека (подробнее в «Спорных решениях»).

## Спорные решения

### 1. Часовые пояса

БД хранит все даты в UTC (`USE_TZ=True`), API отдаёт ISO 8601 с offset'ом. Отображение — в `settings.TIME_ZONE = "Europe/Moscow"` (пояс акции из `PROMO_TZ`).

Пользователь вводит дату через `datetime-local` — это naive-строка без пояса. Считаем, что он имел в виду **время акции** (`PROMO_TZ`), и делаем её aware. Пользователь из Калининграда, вводя «12:00», получит 12:00 по Москве, а не по Калининграду. Обоснование: правила акции формулируются в одном поясе, иначе «до 23:59 31 декабря» превратится в разное время для разных регионов.

Границы периода **включительны с обеих сторон** (`start <= dt <= end`).

### 2. Повторная подача отклонённого чека — разрешена

`UniqueConstraint` на `(fn, fd, fp)` объявлен с `condition=Q(status__in=["pending","accepted"])`. То есть **отклонённые чеки не участвуют в ограничении** — можно подать тот же чек повторно, например, если пользователь исправил фото или заметил ошибку. Форма валидирует уникальность по тому же правилу.

Альтернативный вариант (запретить любую повторную подачу) не выбран, потому что это ухудшает UX без выгоды для бизнеса: модератор всё равно видит историю и может отклонить второй раз.

### 3. API не фильтруется по query-параметрам

`GET /api/receipts/` **всегда** возвращает `Receipt.objects.filter(user=request.user)`. Никакие `?user_id=`, `?all=1`, `?id=` не расширяют выборку — их просто нет в коде. Это защищает от случайной утечки чужих чеков при доработках. Покрыто тестом `test_query_params_dont_leak_other_users` (6 вариантов параметров).

### 4. Порт 8080 вместо 8000

На Windows Docker Desktop / Hyper-V часто резервируют порт 8000, из-за чего `python manage.py runserver` падает с «You don't have permission to access that port». Внутри контейнера порт остаётся 8000, наружу проброшен 8080. Поменять можно в `docker-compose.yml` — строка `ports: "8080:8000"`.

### 5. Миграции на старте контейнера

В `docker-compose.yml` команда `web` — `python manage.py migrate && runserver`. Это удобно для тестового (проверяющий делает `docker compose up` и сразу получает рабочую БД). В проде так делать нельзя: при нескольких репликах миграции стартуют параллельно и могут конфликтовать. Правильно — отдельный job/init-контейнер.

## Работа с ИИ

- **Где помог сильнее всего:** генерация boilerplate — `settings.py`, `Dockerfile`, `docker-compose.yml`, шаблоны, CSS. Это дало примерно 30-40% экономии времени на рутине.
- **Что ИИ выдал неправильно:**
  1. В первом варианте `UniqueConstraint` был без `condition` — блокировал повторную подачу отклонённого чека. Заметил при мысленной проверке сценария «модератор отклонил → пользователь исправил → подал снова» и добавил `condition=Q(status__in=[...])`.
  2. `forms.DateTimeInput` без явных `input_formats` не принимал строку из `<input type="datetime-local">` (формат `YYYY-MM-DDTHH:MM` с буквой T). Поправил вручную.
  3. Первая версия context processor использовала `timezone.localtime(...)`, что дублировало логику с `settings.TIME_ZONE`. Упростил после того, как поменял `TIME_ZONE` на `Europe/Moscow`.
- **Что переписал бы при большем времени:**
  1. Live-обновление статуса чека в кабинете (SSE или короткий polling).
  2. Асинхронная обработка фото (сейчас Pillow синхронно валидирует).
  3. Хранение истории изменений статуса (`ReceiptStatusLog`).
  4. Кеширование списка чеков в API и ETag/Last-Modified.
  5. Полноценный prod-конфиг: gunicorn + nginx + multi-stage Dockerfile + non-root user.

## Что не сделано

- **Live-обновление статуса в кабинете** — упомянуто в «плюсах» ТЗ, не успел. Реализуется за ~30 минут через SSE или setInterval + fetch на `/api/receipts/`.
- **Регистрация пользователей** — по ТЗ дефолтные шаблоны Django, верстки нет.
- **CI (GitHub Actions)** — не требуется, но добавил бы за 15 минут.

## Тесты

```bash
docker compose exec web python manage.py test
```

Покрыто:
- `promo/tests/test_forms.py` — валидация формы (даты, сумма, реквизиты, дубликаты, повторная подача отклонённого);
- `promo/tests/test_views.py` — вьюхи, пагинация, изоляция пользователей, AJAX-ответы;
- `promo/tests/test_api.py` — API, защита от утечки чужих чеков через query-параметры, структура ответа.

## Структура проекта

```
config/                  — настройки Django
promo/
  models.py              — модель Receipt
  forms.py               — ReceiptForm с серверной валидацией
  services.py            — парсер QR, работа с TZ и границами акции
  views.py               — receipt_create, cabinet
  api.py                 — GET /api/receipts/
  admin.py               — админка модератора + CSV-экспорт
  context_processors.py  — параметры акции в контекст шаблонов
  templates/promo/       — base, receipt_form, cabinet
  tests/                 — тесты
static/css/style.css     — стили
static/js/form.js        — валидация + fetch + QR-парсер
docker-compose.yml       — web + db
```
